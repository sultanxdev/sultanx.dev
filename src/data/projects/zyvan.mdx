## Overview

Zyvan is an India-first infrastructure platform for reliable webhook and event delivery.

I'm building Zyvan to handle the parts of webhook systems that become difficult in production — durable event storage, asynchronous processing, retries, idempotency, failure recovery, and observability.

Instead of every engineering team building their own queue workers, retry logic, dead-letter handling, and delivery monitoring, Zyvan provides that reliability layer as a developer-focused platform.

## The Problem

Webhooks are easy when everything works.

The problems start when a destination returns `500`, a request times out, an event is delivered twice, or a customer's service goes offline for hours.

At that point, developers need to answer questions like:

- Was the event received?
- Was it stored safely?
- Was delivery attempted?
- How many times was it retried?
- Why did it fail?
- Can it be replayed?
- Could another tenant's traffic affect this delivery?

Building all of this internally quickly turns a simple webhook endpoint into a distributed system.

I wanted to build the infrastructure layer that handles those failure cases for the developer.

## The Solution

Zyvan sits between an application and its webhook destinations.

A developer sends an event to Zyvan, and the platform takes care of storing, queueing, delivering, retrying, and tracking the event.

The basic workflow is:

**Send Event → Persist → Queue → Deliver → Retry if needed → Recover / Replay**

The goal is to make reliable event delivery available through a simple developer-facing API instead of requiring teams to maintain their own reliability infrastructure.

## Architecture

The system is built around a durable event pipeline that separates ingestion from delivery processing.

The API accepts and persists events first, while background workers handle delivery asynchronously.

PostgreSQL acts as the durable source of truth, while Redis and BullMQ are used for asynchronous processing and delivery orchestration.

The architecture is intentionally modular so individual components can evolve independently as usage grows.

## What I Built

### Durable Event Ingestion

Events are persisted before delivery processing so the system has a durable record of the event lifecycle.

### Asynchronous Delivery

Webhook delivery runs through background workers instead of blocking the API request path.

### Idempotency

Duplicate events are handled using idempotency controls so retries or repeated deliveries don't unnecessarily create duplicate processing.

### Retry Engine

Failed deliveries can be retried using configurable retry behavior with exponential backoff and jitter.

### Dead-Letter Recovery

Events that repeatedly fail are separated from normal processing so they can be inspected and recovered without blocking other events.

### Event Replay

Failed or previously delivered events can be replayed when developers need to recover from downstream failures.

### HMAC Signing

Outbound webhook requests can be signed so receiving applications can verify that requests originated from Zyvan.

### Delivery History

Each event can track delivery status, attempts, response information, and timing for debugging.

### Multi-Tenant Architecture

The platform is designed around organization-level isolation so multiple customers can use the same infrastructure safely.

## Technical Challenges

### Reliable Delivery

The hardest part of webhook infrastructure isn't sending an HTTP request.

It's handling everything that happens when the request fails.

Zyvan treats transient failures, timeouts, duplicate events, and unavailable destinations as expected system conditions rather than exceptional cases.

### Idempotency

Webhook systems operate with at-least-once delivery semantics, which means duplicate events can happen.

The challenge is preventing those duplicates from turning into duplicate side effects.

This led to idempotency being treated as a core part of the delivery design rather than an optional feature.

### Retry Behaviour

Naive retries can make an outage worse.

If thousands of failed events are retried at the same time, the destination can become even more overloaded.

Zyvan uses exponential backoff and jitter to spread retry attempts and reduce retry spikes.

### Queue Backpressure

A destination can process events much slower than they arrive.

The queue provides a buffer between incoming traffic and downstream delivery so temporary differences in processing speed don't immediately propagate back to the application.

This also creates a place to apply rate and concurrency controls.

### Multi-Tenant Isolation

Infrastructure serving multiple customers needs to prevent a high-volume tenant from consuming all available processing capacity.

The architecture therefore considers tenant-level limits and isolation as part of the reliability model.

### Failure Recovery

A failure should not become a permanently lost event.

Events that cannot be delivered normally can move into a recovery path where developers can inspect the failure and replay the event after fixing the destination.

## Reliability Model

Zyvan is designed around the idea that failures are normal in distributed systems.

A webhook destination might:

- Return `500`
- Timeout
- Temporarily go offline
- Recover later
- Receive duplicate events

Instead of treating these situations as lost events, the delivery pipeline keeps the event state visible and moves it through the appropriate retry or recovery path.

This makes the system easier to operate and debug.
