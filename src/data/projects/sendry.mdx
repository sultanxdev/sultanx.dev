## Overview

Sendry is a self-hosted API observability platform designed to capture, process, and analyze API telemetry without making the monitored application's HTTP response wait for database persistence.

The platform uses an event-driven architecture to separate telemetry ingestion from background processing. RabbitMQ handles message buffering, MongoDB stores raw request events, and PostgreSQL maintains pre-aggregated analytics for dashboard queries.

I built Sendry to explore a fundamental backend engineering challenge:

**How do you monitor an application without making the monitoring system a bottleneck for the application itself?**

The solution combines asynchronous telemetry collection, independent background workers, failure handling, and specialized database storage.

## The Problem

API monitoring introduces several engineering challenges as request volume grows.

**Synchronous instrumentation**

Writing telemetry directly to a database during the application's request lifecycle can introduce additional latency and couple application availability to monitoring infrastructure.

**Database bottlenecks**

Raw request events generate write-heavy workloads, while analytics dashboards need efficient read access. Using the same storage and query strategy for both workloads can become inefficient.

**Traffic spikes and failures**

A sudden increase in telemetry volume or a database outage can overwhelm directly connected processing systems.

**Observability costs**

Commercial observability platforms can become expensive as event volume increases, while self-hosted alternatives can require significant operational effort.

## The Solution

Sendry separates telemetry collection, message publishing, event processing, storage, and analytics into independent components.

The main design decisions are:

- **Asynchronous ingestion:** Telemetry submission is scheduled after the monitored application's response has finished.
- **Message buffering:** RabbitMQ separates event ingestion from background processing.
- **Independent persistence:** Background workers manage database writes without blocking ingestion.
- **Dual-database architecture:** MongoDB stores raw events, while PostgreSQL stores structured analytics.
- **Failure isolation:** Circuit breakers, retries, and dead-letter queues handle infrastructure failures.
- **Pre-aggregated analytics:** Dashboard queries use hourly metrics rather than repeatedly scanning raw event data.

The monitored application's response does not wait for telemetry persistence. The SDK still uses application resources to submit telemetry asynchronously.

## System Architecture

Sendry is organized around four major processing layers:

1. **Ingestion:** Receives telemetry, validates API keys, and publishes events.
2. **Messaging:** RabbitMQ buffers events between ingestion and processing.
3. **Processing and Storage:** Background workers process events and coordinate database persistence.
4. **Analytics:** The backend serves pre-aggregated metrics to the React dashboard.

![Sendry System Architecture](/project/sendry/architecture.svg)

### Core Components

**Sendry SDK**

A lightweight Express.js middleware that observes HTTP responses, captures request metadata, calculates request duration, and schedules telemetry submission.

**Ingestion API**

An Express.js endpoint that validates API credentials and publishes telemetry to RabbitMQ using publisher confirmation.

**RabbitMQ**

Acts as the messaging layer between ingestion and background processing, allowing incoming events to be buffered independently of database operations.

**Background Worker**

Consumes queued messages, applies processing and retry logic, and coordinates writes to MongoDB and PostgreSQL.

**MongoDB**

Stores raw API request events and metadata using document-based storage and a 30-day TTL retention policy.

**PostgreSQL**

Maintains structured hourly analytics using SQL aggregation and UPSERT operations.

**React Dashboard**

Displays API monitoring information using data retrieved through the analytics API.

## Request Ingestion Flow

The ingestion lifecycle is designed so the monitored application's original HTTP response does not wait for telemetry processing or database persistence.

![Sendry Request Ingestion Sequence](/project/sendry/sequance.svg)

### How It Works

1. A client sends an HTTP request to the monitored application.
2. Sendry SDK middleware observes the response `finish` event.
3. The middleware calculates request duration using `process.hrtime()`.
4. The monitored application completes its response to the original client.
5. The SDK schedules a separate telemetry request using `setImmediate()`.
6. Sendry Ingest API validates the API key.
7. The ingestion API publishes the event to RabbitMQ using a publisher confirm channel.
8. After successful publishing, the ingestion API responds with `202 Accepted`.
9. A background worker consumes the message.
10. The worker stores raw event data in MongoDB and updates hourly analytics in PostgreSQL.

This separation prevents the original application response from depending on downstream database writes.

## What I Built

### 1. Lightweight Telemetry SDK

Implemented an Express.js middleware to capture API request information, including:

- HTTP method and endpoint.
- Response status code.
- Request duration.
- Request metadata and payload-size information.
- Client information where configured.

Request duration is calculated using Node.js high-resolution timing.

The middleware observes the completed response and schedules a separate telemetry submission rather than waiting for the monitoring database operations.

### 2. Event-Driven Ingestion Pipeline

Built a separate ingestion API that validates credentials and publishes telemetry messages to RabbitMQ.

The ingestion layer does not perform raw event database writes.

Publisher confirmation is used to verify message publishing before returning `202 Accepted` to the SDK.

This separates the responsibilities of accepting telemetry and persisting it.

### 3. Circuit Breaker

Implemented an ingestion-side circuit breaker to handle RabbitMQ availability failures.

It uses three states:

- **CLOSED:** Normal message publishing.
- **OPEN:** Stops publishing after the configured failure threshold.
- **HALF-OPEN:** Sends probe messages to determine whether the broker has recovered.

Configured behavior:

- Five broker failures within a 10-second window.
- 30-second recovery cooldown.
- Three recovery probe messages.

If the broker remains unavailable, the ingestion API fails fast rather than allowing requests to wait indefinitely.

### 4. Retry Strategy and Dead-Letter Queue

Implemented exponential backoff with randomized jitter for transient processing failures.

The retry delay uses:

\[
delay = (baseDelay \times 2^{attempt}) \times (1 + random(-0.3, 0.3))
\]

The ±30% jitter helps distribute retry attempts and reduces synchronized database recovery spikes.

Messages that fail validation or exhaust their configured retry attempts are routed to the Dead-Letter Queue.

**DLQ:** `api_hits.dlq`

Failure metadata is attached through message headers:

- `x-dlq-reason`
- `x-dlq-error`

This keeps problematic messages separate from normal queue processing.

### 5. Dual-Database Architecture

Designed the storage layer around two different data access patterns.

**MongoDB — Raw Event Storage**

- Stores raw API request events and metadata.
- Supports flexible document structures.
- Uses a 30-day TTL index.
- Automatically expires old records using `expireAfterSeconds: 2592000`.

**PostgreSQL — Analytical Storage**

- Stores structured hourly metrics.
- Uses SQL UPSERT operations.
- Maintains pre-aggregated analytics.
- Avoids repeatedly scanning raw event documents for dashboard queries.

The two databases serve distinct responsibilities rather than forcing raw event logging and analytical queries into one storage model.

### 6. Duplicate Message Filtering

RabbitMQ uses at-least-once delivery semantics, so duplicate message deliveries must be considered.

Implemented a bounded in-memory FIFO `Set` to filter duplicate messages using unique message UUIDs.

The cache has a maximum capacity of 100,000 entries, with MongoDB uniqueness constraints providing additional protection for raw event storage.

**Engineering trade-off:** The in-memory cache is lost when a worker restarts. It is a fast duplicate-filtering mechanism, not a complete durable idempotency guarantee for PostgreSQL aggregate updates.

### 7. Analytics Dashboard

Built a React dashboard using:

- **React:** Frontend application.
- **TanStack Query:** Server-state management.
- **ApexCharts:** Analytics visualization.
- **Tailwind CSS:** Responsive interface styling.

The dashboard presents API monitoring information such as request volume, error rates, latency percentiles, endpoint traffic, and service health.

Analytics are served from pre-aggregated PostgreSQL records.

## Engineering Decisions & Trade-offs

### Why RabbitMQ instead of direct database writes?

Direct database writes would couple event ingestion to database availability and performance.

RabbitMQ provides a separate buffering and delivery layer, allowing background consumers to process events independently.

The trade-off is additional infrastructure and broker operations.

### Why MongoDB and PostgreSQL?

Raw telemetry and analytical queries have different storage requirements.

MongoDB provides flexible raw event storage, while PostgreSQL supports structured aggregations and relational querying.

The trade-off is the additional operational complexity of maintaining two databases and handling cross-database consistency.

### Why in-memory duplicate filtering?

A database lookup for every message would introduce additional database operations into the consumer processing path.

A bounded in-memory cache makes duplicate filtering inexpensive, but its state is ephemeral and requires a durable strategy for stronger idempotency guarantees across worker restarts.

## Performance & Engineering Characteristics

Sendry's architecture is designed around the following properties:

- Telemetry persistence happens outside the original application response path.
- RabbitMQ buffers messages between ingestion and database processing.
- Background workers operate independently of the ingestion API.
- Raw event retention is bounded through MongoDB TTL indexes.
- Hourly PostgreSQL aggregation reduces repeated analytical query work.
- Retry and circuit breaker mechanisms provide controlled failure handling.

Performance figures such as throughput, ingestion latency, and dashboard query latency should be evaluated using reproducible benchmarks under a documented workload and hardware configuration.

## Technical Challenges

### Keeping monitoring failures isolated

A monitoring system should not become a dependency that prevents the monitored application from serving requests.

The main challenge was separating telemetry submission from the application's response lifecycle while handling infrastructure failures.

The solution combines response-finish instrumentation, asynchronous telemetry submission, and a circuit breaker around message publishing.

### Handling duplicate message deliveries

At-least-once message processing means consumers must account for repeated deliveries.

The bounded in-memory UUID cache avoids repeated processing for recently seen messages without performing a database lookup for each duplicate.

The remaining limitation is persistence of deduplication state across worker restarts.

### Keeping analytical queries efficient

Repeatedly scanning raw event collections for dashboard requests creates unnecessary query work.

Hourly aggregation in PostgreSQL moves analytical computation into the processing pipeline, allowing the dashboard to retrieve structured metrics.

### Managing cross-domain authentication cookies

Frontend and API development environments can run on different ports or domains.

Implemented environment-aware cookie configuration to handle local development and production cross-site cookie scenarios.

## What I Learned

Building Sendry required me to think beyond API endpoints and frontend functionality.

The most important engineering lesson was that decoupling is not just a scalability technique; it is also a way to isolate failures and define clear system boundaries.

Working with RabbitMQ, independent background workers, circuit breakers, retry strategies, and multiple databases helped me understand the practical trade-offs involved in building event-driven backend systems.

It also reinforced the importance of designing for failure rather than assuming every infrastructure component will always be available.
