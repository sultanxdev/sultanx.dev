# The Saga Pattern: Managing Distributed Transactions in Node.js

What do you do when a single business operation — like placing an order — spans three different services with three different databases? You can't use a traditional database transaction. You can't rely on "hope it works." You need a Saga.

In this post, I'll walk you through how I implemented the **Saga orchestration pattern** in my project Eventify — a distributed order processing system built with Node.js and Kafka.

## Why Traditional Transactions Don't Work

In a monolith, this is straightforward:

```javascript
// Monolith: one database, one transaction
await db.transaction(async (tx) => {
  await tx.orders.create(orderData);
  await tx.inventory.reserve(items);
  await tx.payments.charge(amount);
  // Either ALL succeed, or ALL roll back
});
```

But in microservices, each service owns its own database. There's no shared transaction scope. If the payment service fails after inventory is reserved, you have **inconsistent state** across services.

This is the **distributed transaction problem**, and the industry-standard solution is the **Saga pattern**.

## What Is a Saga?

A Saga is a sequence of local transactions where:

1. Each step is a local transaction in one service
2. Each step publishes an event or triggers the next step
3. If a step fails, **compensating transactions** undo the previous steps

Think of it like booking a trip: you book a flight, then a hotel, then a car. If the car rental fails, you cancel the hotel, then cancel the flight. Each cancellation is a "compensation."

## Orchestration vs Choreography

There are two ways to coordinate a Saga:

**Choreography** — each service listens for events and decides what to do next. No central coordinator. Simple, but hard to debug when things break.

**Orchestration** — a central coordinator (the orchestrator) tells each service what to do and when. More explicit, easier to reason about.

I chose **orchestration** for Eventify because:
- The workflow is clearly visible in one place
- Failure handling is explicit, not scattered
- Adding new steps doesn't require touching existing services
- It's much easier to debug

## Implementing the Order Saga

Here's the orchestrator — the Order Service that drives the entire workflow:

```javascript
// order-saga.js — The Saga Orchestrator
class OrderSaga {
  constructor(kafka, db) {
    this.producer = kafka.producer();
    this.db = db;
  }

  async start(orderData) {
    // Step 1: Create order in PENDING state
    const order = await this.db.orders.create({
      ...orderData,
      status: 'PENDING',
      sagaState: 'INVENTORY_PENDING',
    });

    // Step 2: Request inventory reservation
    await this.producer.send({
      topic: 'inventory.reserve',
      messages: [{
        key: order.id,
        value: JSON.stringify({
          orderId: order.id,
          items: orderData.items,
          correlationId: order.id,
        }),
      }],
    });

    return order;
  }

  async onInventoryReserved(event) {
    const { orderId } = event;

    // Update saga state
    await this.db.orders.update(orderId, {
      sagaState: 'PAYMENT_PENDING',
    });

    // Step 3: Request payment
    const order = await this.db.orders.findById(orderId);
    await this.producer.send({
      topic: 'payment.charge',
      messages: [{
        key: orderId,
        value: JSON.stringify({
          orderId,
          amount: order.totalAmount,
          correlationId: orderId,
        }),
      }],
    });
  }

  async onPaymentCompleted(event) {
    const { orderId } = event;

    // All steps succeeded — mark order as CONFIRMED
    await this.db.orders.update(orderId, {
      status: 'CONFIRMED',
      sagaState: 'COMPLETED',
    });
  }
}
```

The saga progresses through explicit states: `INVENTORY_PENDING` → `PAYMENT_PENDING` → `COMPLETED`. At each step, the orchestrator knows exactly where the order is.

## The Transactional Outbox Pattern

There's a subtle but critical problem: **how do you reliably publish events?**

```javascript
// ❌ The dual-write problem
await db.orders.create(order);     // What if this succeeds...
await kafka.send(event);           // ...but this fails?
```

If the database write succeeds but Kafka publish fails, you have an order with no event — the saga stalls silently.

The solution is the **Transactional Outbox**: write the event to a database table in the same transaction as the business data, then publish from the table separately.

```javascript
// ✅ Transactional Outbox
await db.transaction(async (tx) => {
  // Business write
  const order = await tx.orders.create(orderData);

  // Event write — SAME transaction
  await tx.outbox.create({
    topic: 'inventory.reserve',
    key: order.id,
    payload: JSON.stringify({
      orderId: order.id,
      items: orderData.items,
    }),
    published: false,
  });
});

// Separate background worker publishes from outbox
async function outboxPublisher() {
  const unpublished = await db.outbox.findMany({
    where: { published: false },
    orderBy: { createdAt: 'asc' },
  });

  for (const event of unpublished) {
    await kafka.send({
      topic: event.topic,
      messages: [{ key: event.key, value: event.payload }],
    });

    await db.outbox.update(event.id, { published: true });
  }
}
```

Now the business data and the event are atomic. The background publisher runs on a schedule and retries if Kafka is temporarily unavailable.

## Making Consumers Idempotent

Kafka delivers messages **at least once**. Your consumer will see the same event multiple times — during rebalances, retries, or network issues.

Every service in Eventify tracks processed events:

```javascript
// Idempotent consumer wrapper
async function processEvent(event, handler) {
  const { correlationId } = event;

  // Check if already processed
  const existing = await db.processedEvents.findByCorrelationId(correlationId);
  if (existing) {
    console.log(`Event ${correlationId} already processed, skipping`);
    return;
  }

  // Process in a transaction
  await db.transaction(async (tx) => {
    // Run the actual business logic
    await handler(event, tx);

    // Mark as processed — SAME transaction
    await tx.processedEvents.create({
      correlationId,
      processedAt: new Date(),
    });
  });
}

// Usage
consumer.on('inventory.reserve', async (message) => {
  const event = JSON.parse(message.value);
  await processEvent(event, async (data, tx) => {
    await tx.inventory.reserve(data.items);
  });
});
```

The `processed_events` table acts as a deduplication log. Because the business logic and the deduplication write are in the same transaction, it's impossible to process an event twice.

## Handling Failures with Compensation

The real power of Sagas is graceful failure handling. If payment fails after inventory is reserved, we need to **compensate** — release the reserved inventory:

```javascript
async onPaymentFailed(event) {
  const { orderId, reason } = event;

  // Update saga state
  await this.db.orders.update(orderId, {
    sagaState: 'COMPENSATING',
  });

  // Compensate: release reserved inventory
  await this.producer.send({
    topic: 'inventory.release',
    messages: [{
      key: orderId,
      value: JSON.stringify({
        orderId,
        correlationId: orderId,
      }),
    }],
  });
}

async onInventoryReleased(event) {
  const { orderId } = event;

  // Compensation complete — mark order as FAILED
  await this.db.orders.update(orderId, {
    status: 'FAILED',
    sagaState: 'COMPENSATED',
    failureReason: 'Payment declined',
  });
}
```

The saga state machine now looks like:

```
PENDING
  → INVENTORY_PENDING
    → PAYMENT_PENDING
      → COMPLETED ✅
      → COMPENSATING → COMPENSATED ❌
    → COMPENSATING → COMPENSATED ❌
```

Every failure path has a clear recovery path. No orphaned state, no silent failures.

## Lessons Learned

1. **Orchestration > Choreography** for complex workflows — the visibility is worth the trade-off
2. **The Transactional Outbox** is non-negotiable — never dual-write to a DB and a message broker
3. **Idempotency is a requirement**, not an optimization — at-least-once delivery means your consumers will see duplicates
4. **Model your saga states explicitly** — if you can't draw the state machine, you can't debug failures
5. **Design compensations upfront** — not every operation is reversible, and that affects your architecture

Building Eventify showed me that distributed systems aren't about avoiding failures — they're about **designing for failures**. The Saga pattern gives you a structured way to do exactly that.
